# Energy Intelligence local development

This increment uses a configured web-search provider to discover first-party source links, saves source evidence behind an authenticated interface, and uses a separately configured analysis provider to create Chinese intelligence tied to exact source quotations. A human note remains optional. Single-source results are labeled as not cross-validated and do not become a commercial opportunity automatically. When a second candidate shares a country, a concrete project name and an organization, the analysis provider compares only the two saved fact sets; accepted matches and conflicts must reference fact numbers from both sources.

## Setup

1. Use Node.js 24 and `npm ci`.
2. Use an isolated development Supabase project or the official local Supabase stack. Apply the files in `supabase/migrations/` in filename order using an administrator database connection.
3. Disable public signups. Create one email/password user through the Supabase administrator interface and copy its user UUID. The API accepts only this explicitly configured user, regardless of other project users.
4. Copy `.env.intelligence.example` to `.env.local`. Set the project URL, anon key, service role key and permitted user UUID. These are server-only settings. The service role key bypasses RLS and must never appear in a browser bundle, report or Git commit.
5. Set `NRGOPT_APP_ORIGIN` to the exact browser origin (local default `http://127.0.0.1:4317`), and enable development imports with `NRGOPT_INTELLIGENCE_WRITE_ENABLED=1`. Production stays read-only unless both that switch and the separate `NRGOPT_INTELLIGENCE_PRODUCTION_WRITE_ENABLED=1` release switch are present.
6. Configure the initial discovery and analysis profiles with the `NRGOPT_DISCOVERY_*` and `NRGOPT_ANALYSIS_*` variables shown in `.env.intelligence.example`. Discovery requires an Anthropic Messages-compatible endpoint with hosted `web_search`; analysis requires a Chat Completions-compatible endpoint that can return JSON. `MINIMAX_API_KEY` and `DEEPSEEK_API_KEY` remain legacy key fallbacks only for the unchanged default profiles.
7. Generate 32 random bytes, encode them as base64 and set `NRGOPT_PROVIDER_CONFIG_KEY` only in the server environment. The private `/intelligence/settings` page uses it to encrypt administrator-entered API keys with AES-256-GCM before database storage. The key is write-only in the browser and is never returned by the API. Changing this encryption key without first replacing the saved provider keys makes existing saved profiles unusable.
8. Run `npm run dev:intelligence`, then visit `/intelligence`. Only loopback is served. Log in with the user created above. No email is sent by this application.

Paid model calls are hard-stopped until the active service profile has an enabled monthly amount limit. Discovery and analysis have separate limits; extraction and cross-checking share the analysis limit. The server chooses a conservative per-call reservation internally and releases the unused amount when usage is settled. Each profile declares `CNY` or `USD`; the system never converts between currencies. The known default MiniMax M3 and DeepSeek Flash profiles can settle from returned usage using dated pricing; a custom provider or model settles the internal reservation until its pricing rule is explicitly implemented.

The scheduler endpoint is `GET /api/intelligence?action=scheduled-scan`. It requires `NRGOPT_SCHEDULER_ENABLED=1` and `Authorization: Bearer $CRON_SECRET`; one invocation claims and finishes at most one persisted item. A country discovery item adds deduplicated `source:<url-hash>` items, a source item fetches and saves one original page and adds one `extract:<source-id>` item, and an extraction item sends only that saved evidence to the configured analysis provider. No production cron schedule is included in this increment because the current Vercel plan and function duration have not been approved for the required consumer cadence.

The independent `GET /api/intelligence?action=health-check` endpoint uses the same bearer secret but does not depend on the daily scan handler. It checks whether today's run exists and whether it completed successfully. Missing or terminal degraded runs create one idempotent `system` outbox item; healthy or still-running jobs do not send a false alert. An external schedule is still required to invoke this endpoint after the expected scan window.

For local archive validation, set `NRGOPT_ARCHIVE_ENABLED=1`, a server-only `NRGOPT_ARCHIVE_TOKEN`, node ID, base URL and absolute private archive directory. Run `npm run archive:intelligence`. The client downloads only its claimed object, verifies size and SHA-256, writes the object and manifest atomically, then acknowledges. Re-running an empty queue writes nothing. Completion never deletes the cloud object and therefore does not claim that a single Mac copy is a backup.

Feishu delivery stays off until `NRGOPT_FEISHU_ENABLED=1` and an authorized official custom-bot webhook are stored server-side. `GET /api/intelligence?action=notification-worker` uses the scheduler bearer secret, claims one outbox row and records accepted, retry, failed or unknown. Network loss after sending is recorded as unknown and is not blindly retried. The repository tests use a fake webhook only and do not send a real message.

The cloud project is not provisioned by this change. No deploy command or automatic database migration runs from the application. Production writes require two explicit server-side switches and remain disabled by default; production release remains a separate decision.

## Behavior and limitations

- Source import accepts public HTTPS port 443, UTF-8 HTML or plain text, up to 2 MiB, 3 redirects and 25 seconds. PDF, compressed responses and JavaScript-rendered articles are not supported in this increment.
- If a page has no readable body but publishes its article text in standard `description` or `og:description` metadata, that metadata is extracted without executing page scripts. This supports official SPA pages while keeping the saved original unchanged.
- Source discovery calls the configured Anthropic Messages-compatible endpoint with the hosted `web_search` tool. Search summaries are treated only as link leads. The API keeps only configured government, official news agency, utility, owner and project-company domains for each GCC country; a selected result is fetched again before any evidence is stored.
- A saved settings-page profile overrides the corresponding environment profile. The server decrypts its API key only for an authorized provider call. Invalid ciphertext, a missing encryption key or an incomplete profile fails closed before any provider request.
- Each redirect is DNS-checked and the request is pinned to a checked public address. Source HTML is parsed as text, never executed.
- The original response body is stored in a private bucket. The database keeps URL, fetch timestamp, hash, title and a source excerpt. Publication date remains unknown. These fields are source metadata, not verified facts or model output.
- An optional Chinese note can record the user's own business judgment. It remains separate from the original title, excerpt and model output, and reading intelligence does not require manual approval.
- Model extraction runs after the authorized user clicks the extraction button, or when a persisted scheduled extraction item is claimed. Up to 12,000 characters of the saved public source, its title and URL are sent to the configured analysis endpoint. Private notes, login details and stored credentials are not sent. The direct HTTP integration uses a Chat Completions-compatible JSON request with bounded structured extraction; there is no external AI SDK dependency.
- The analysis provider returns structured Chinese fields for the change summary, relevance, known facts, unknowns, hypotheses and next signals. Every known fact must include a quotation that occurs in the submitted source text after whitespace normalization. If any required field or quotation fails validation, the entire result is rejected and only a stable error code is saved. Manual extraction can be retried explicitly; a scheduled extraction retries only its own persisted item, up to the job-item ceiling.
- Accepted model output stores the provider, model, source SHA-256 and token counts. Token counts remain server-private. The UI identifies whether evidence is a single source, cross-validated or conflicting, and continues to show the optional human note separately.
- G2 classification adds a separate review candidate. It can use trigger, demand and project radars and the six country codes `SA`, `AE`, `QA`, `KW`, `OM`, `BH`. An occurrence country, organization, project or procurement must point to a numbered known fact whose quotation already passed exact source validation. Global background with no GCC occurrence is stored as `source_only` and does not enter country or radar counts.
- `/intelligence/overview` always renders all six countries and shows only evidence-backed candidates. Candidate importance, evidence state, maturity and urgency remain separate dimensions. A validated candidate is marked `auto_validated`; it does not wait for mandatory user approval and still does not automatically create a commercial opportunity.
- G2 tables include candidates, hypotheses, watch targets, organizations and aliases, projects, procurement packages and explicit candidate-to-candidate evidence relations. A validated extraction automatically upserts its explicitly named organizations and project, then replaces that project's procurement package with the current evidence-linked value. Ambiguous multi-country projects remain candidates instead of being forced into a formal project country. Conservative organization matching handles case, legal suffixes and explicit parenthetical acronyms while retaining every observed name as an alias; transliteration and ambiguous business-unit names are not merged automatically.
- The cross-source prefilter requires the same occurrence country, at least one shared concrete project token and at least one shared organization token. The configured analysis provider then compares only saved fact arrays. A conflict requires an incompatible value for the same project, field, time and scope; a later project stage, a project-group subset, or equivalent `MW × hours` and `MWh` values are not conflicts. The overview label says “部分事实已交叉核对” because the status does not claim every statement is independently confirmed.
- The same owner, final URL and content hash reuse one record. Changed content creates a version. A scheduled source item does not enqueue another analysis task when that exact content hash already has a successful extraction. Failed fetches or storage attempts remain visible; retry the URL to recover a failed storage attempt.
- An access token is held only in an HttpOnly, SameSite=Strict cookie (Secure over HTTPS), for at most one hour. Expiry requires login again. The Supabase user is checked on every protected request. Logout clears the browser cookie and revokes the upstream session's refresh ability; an already issued access token may remain valid until expiry.
- The list shows the newest 50 records. Evidence is served only after login and a SHA-256 check, as a download with `nosniff` and a sandbox policy.
- Database RLS grants no direct anon/authenticated access; only the server service role reads/writes. It always applies the allowed user's owner filter. No public storage policy is created.
- G3 adds idempotent daily job runs, staged country/source/extraction items, leases, checkpoints and a three-attempt retry ceiling. URL hashes prevent duplicate discovery results from creating duplicate source work, and unchanged extracted content does not queue another paid extraction. Atomic budget reservations guard manual and scheduled paid calls; if extraction budget is unavailable, saved evidence remains intact while only that extraction item pauses. Settled reservations retain provider, model, bounded usage counters and the dated price version without exposing them to the browser. The overview exposes recent task, budget and notification state without exposing keys.
- Candidate FLASH registration uses a database trigger, so a qualifying candidate and its outbox row commit together. The initial gate is `critical`, or `high` with `prepare`/`deadline` urgency. Daily notification keys are tied to the schedule date; repeated scheduler compensation does not duplicate the logical summary.
- Every successfully saved evidence object gets an archive job. Existing evidence is backfilled by the archive migration. The Mac token can only use the archive API; it is separate from browser login and the Supabase service role.

## Verification

`npm test` runs existing regressions plus source security, API authorization, job/budget, notification and archive tests. Local validation must also apply the migrations to a real Supabase stack and exercise the RPCs; unit tests alone do not prove transaction or PostgREST behavior.

`tests/fixtures/intelligence-quality-v1.json` is the initial three-language baseline: one attributed official excerpt each in English, Chinese and Arabic, with manually recorded expected facts and exact quotations. Its offline test checks provenance fields, language coverage and quotation integrity. It is only a starter set and does not satisfy the PRD recommendation for a representative 60-item release corpus or produce an accuracy/recall score.

For real integration: log in, use the configured discovery provider for one GCC country, save one first-party result, reopen the private detail page, download and compare its SHA-256, repeat import and verify one record, then run extraction. Confirm every displayed evidence quotation occurs in the saved source and the stored extraction hash matches that source. Add an independent official source for a named project and confirm the relation records fact-number pairs from both sides; a stage progression or equivalent unit expression must not be shown as a conflict. Verify the model panel remains separate from the optional human note. Log out and confirm detail/API/evidence require login. Verify direct anon and ordinary authenticated requests cannot read either the table or bucket. Check failed source imports and retry behavior.

Do not store private product documents, conversations, downloaded evidence or credential files in this public repository. Do not use contact/SMTP routes during local testing.
